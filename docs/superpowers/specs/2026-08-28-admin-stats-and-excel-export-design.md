# 관리자 통계 대시보드 + 엑셀 내보내기

작성일: 2026-08-28

## 배경

`/admin/analytics`가 이미 있지만 숫자 카드와 표뿐이라 추이를 읽을 수 없다. 데이터를 엑셀로 빼는 경로는 어디에도 없다.

작업 중 기존 문제 하나를 발견했다. 분석 서비스들이 모두 `activityEventLogger.getRecentEvents(3000)`으로 **최근 3000건만 메모리에 올려 필터**한다([job-analytics.service.ts:33](../../../src/services/job-analytics.service.ts)). 2026-08-28 기준 `activity_events`는 사흘치 1,926건이다. 이 속도면 몇 주 안에 상한을 넘고, 그 순간부터 모든 통계가 조용히 "최근 3000건 기준"으로 바뀐다. 경고도 표시도 없다. 새 대시보드를 이 위에 얹으면 그대로 물려받으므로, 새로 만드는 집계는 SQL로 내린다.

## 결정

- 대상은 **관리자만**. 회원용 내보내기는 만들지 않는다.
- 엑셀은 **목록 시트 + 요약 시트**를 한 파일에 담는다. CSV로는 시트 탭이 없어 불가능하므로 xlsx 생성기를 쓴다.
- 통계는 **새 페이지 `/admin/stats`** 로 만들고 기존 `/admin/analytics`는 상세 표로 남긴다. 두 화면이 **같은 스냅샷 서비스를 호출**하게 해서 숫자가 갈라질 수 없게 한다.
- 채용공고는 전량(6만 건)을 내보내지 않는다. **상세가 열린 공고만** 담고 관심 지표를 열로 붙인다.

## 데이터 계층

기존 스냅샷 서비스 10개는 그대로 재사용한다. 없는 것만 새로 만든다.

### `admin-stats.service.ts` — 기간별 추이

`activity_events`를 `date_trunc('day')`로 그룹핑해 일자 × 이벤트종류 카운트를 받는다. PostgREST는 group by를 지원하지 않으므로 Supabase RPC(SQL 함수)로 둔다. 클라이언트로 끌어와 세면 지금의 3000건 문제를 되풀이한다.

### `job-interest.service.ts` — 공고별 관심 집계

`activity_events`에서 `entity_type = 'job'`을 공고 id로 그룹핑해 순방문자·조회수·북마크·지원클릭을 낸다. 그 id 목록으로만 `jobs`를 조회한다 — 공고 전체 조회는 타임아웃 나므로 금지다.

순방문자는 `coalesce(user_id::text, anonymous_id)`로 센다. 조회수 총합은 한 사람의 연타로 쉽게 오염되지만 순방문자는 그렇지 않다.

## 통계 페이지 `/admin/stats`

세 구역으로 나눈다.

| 구역 | 답하는 질문 | 내용 |
|---|---|---|
| 얼마나 쓰나 | 이용량과 추이 | 일자별 선그래프(진단 완료·공고 조회·지원금 진단·이력서), 기간 7/30/90일 |
| 어떤 사람들인가 | 회원 구성 | 연령대·지역·취업상태 분포 막대, 세그먼트별 활동량 |
| 어디서 새나 | 이탈 지점 | 가입 → 진단시작 → 완료 → 결과열람 → 지원 퍼널 |

차트는 recharts를 쓴다. 이미 shadcn을 쓰고 있어 표준 조합이다.

## 엑셀 내보내기

`/api/admin/export/[domain]` 라우트. `requireAdmin` 뒤에 두고 exceljs로 생성한다.

| 도메인 | 목록 시트 | 요약 시트 |
|---|---|---|
| 직업진단 | 세션별 응답·결과 | 문항별 응답 분포 |
| 채용공고 | 상세 열린 공고 전부 + 깔때기 열 | 직종·지역·급여대 집계 |
| 지원금 | 진단 세션별 답변·매칭 결과 | 제도별 조회·신청 클릭 |
| 이력서 | 이력서별 완성도·AI첨삭 사용 | 템플릿·연령대 집계 |

공고 시트 열: 공고명 / 회사 / 직종 / 지역 / 급여 / 순방문자 / 조회수 / 1인당조회 / 북마크 / 지원클릭 / 지원전환율 / 마감여부.

**1인당조회**와 **지원전환율**이 이 시트의 요점이다. "많이 봤는데 아무도 지원하지 않은 공고" — 제목은 끌리는데 조건에서 걸린 공고 — 가 드러난다.

## 개인정보

내보내기 파일에 이름·연락처·이메일을 넣지 않는다. 회원 식별이 필요한 시트는 `profiles.id` 앞 8자리만 쓴다. 관리자 화면에는 이미 CRM 상세가 있으므로 개인 식별은 그쪽에서 하고, 내보내기는 집계·분석용으로 한정한다.

## 오류 처리

- 집계 RPC 실패 시 페이지는 빈 차트 대신 "집계를 불러오지 못했습니다"를 구역 단위로 표시한다. 한 구역이 실패해도 나머지는 보여준다.
- 내보내기 실패는 500이 아니라 관리자 화면에 사유를 보여준다. 파일이 안 받아지는 것과 빈 파일이 받아지는 것은 구분돼야 한다.
- 내보낼 행이 0건이면 시트에 헤더만 남기고 "해당 기간 데이터 없음" 행을 한 줄 넣는다.

## 범위 밖

- 회원용 내보내기
- 예약 발송·이메일 첨부
- 기존 `/admin/analytics` 개편 (남겨둔다)
- 기존 분석 서비스의 3000건 상한 제거 — 새 집계는 SQL로 가지만, 기존 스냅샷 10개를 전부 옮기는 것은 별건이다. 이번 작업에서 발견 사실만 기록한다.
